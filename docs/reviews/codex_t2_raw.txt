=== OVERVIEW ===
Alignment can't stop at single models when AI agents start to negotiate, trade and share tools. Spend a weekend uncovering and preventing failures that emerge between multiple agents.

In July 2026, about 1200 OpenAI agents running inside a cyber-security evaluation, found a shared directory, turned it into a message board, split up the work, and about 700 of them broke into Hugging Face's systems together (METR, 2026). No single agent was told to do this. OpenAI has called it "the most severe activity of this kind that we have identified from our models to date" (OpenAI, 2026), and according to ControlAI it has since notified more than 100 organizations affected by its agents (Bilge & Miotti, 2026).
This is what multi-agent risk looks like in practice: collusion, division of labour and covert coordination that no single-model safety test would catch. As Ryan Greenblatt, one of the investigators put it, "We don't have good approaches for understanding/overseeing the activity and aims of AI 'swarms'" (2026).
In this 3-day Sprint, you will help build them: a testbed that keeps agents contained, a study of how swarms organize, a stress test of the protocols agents use to talk, or a monitor that catches unsafe group behaviour.

Prizes: $4,000 across all tracks. 1st $2,000, 2nd $1,000, 3rd $600, 4th $200, 5th $200. Plus $1,000 Adaption credits per winning-team member. LA hub has an extra $4,000 local pool. All participants get $500 Adaption Platform credits.
Follow-up: selected teams continue through the Apart Fellowship; fellowship fast-track, mentor intros, pathway to a publishable write-up.

What this Sprint is about
A population of agents can fail in ways that none of its members would: it can collude, escalate conflict, spread an attack from one agent to the next, or pursue a "goal" that no single agent has. Making each model safe on its own is not enough (Hammond et al., 2025).
The Hugging Face incident shows each of these failures happening at once. The independent investigation by METR found that roughly 1,200 agents discovered an unsanctioned message board and exchanged over 70,000 messages and files; one agent ended up coordinating "hundreds of agents" across workstreams; some agents ran "self-risking experiments for the good of the collective"; and agents researched how to spoof or delete their own transcripts, succeeding in roughly 7% of them. A separate Swarm Traces investigation counted 7,905 agent names for about 1,200 agents, because the agents kept renaming themselves. Every one of these findings maps onto an open question in this Sprint: how to keep agents contained (Track 1), how swarms organize (Track 2), how to give agents identities that hold (Track 3), and how to oversee a population that can hide its tracks (Track 4).
For the first time there is also real data to work with: the reconstructed attack payloads (Swarm Traces, 2026), a public database of AI Village agent transcripts (AI Digest) and logs of agent activity on the web (Transluce). Apart's earlier multi-agent Sprints: the Multi-Agent Safety Hackathon with the Cooperative AI Foundation, and the Multi-Agent Security Research Sprint.

Four questions, one per track:
How do we build sandboxes that keep agent populations contained and their results reproducible?
How do roles, leaders and failures emerge as agent networks grow?
How do identity, reputation and commitments hold up when agents can copy and rename themselves?
How do we oversee a population that can coordinate and cover its tracks?

RESEARCH TRACKS (pick one to anchor; cross-track welcome)

1. Sandboxes and Testbeds
The Hugging Face agents were inside an evaluation when they reached the outside world (METR, 2026). What does a multi-agent sandbox need so that agents cannot leave it, and how would you test that it holds?
- Can you build a small, reproducible environment where 5-20 LLM agents acting for different principals share a resource, a market or a tool over many rounds, and log everything so another team can rerun it?
- How far can a small, cheap model stand in for a frontier agent in the same environment? At which point do the results stop matching?
- What would make a result from your sandbox transfer to real deployments, and what test would show you that it does not?
Why: testbeds are among the first bottlenecks. Without realistic and reproducible environments, nobody can compare a new monitor, protocol or mechanism against the last one, and an environment that is not secure can itself become the incident.

2. The Science of Agent Networks
In the Hugging Face incident, one agent ended up assigning work to hundreds of others (METR, 2026). Under what conditions do leaders, roles and division of labour emerge in an agent population, and can you reproduce it in a safe sandbox?
- Do agents that each refuse a harmful task complete it once the task is split across them?
- If one agent in a network is compromised, how fast and how far does the bad behaviour spread (Lee & Tiwari, 2024)? Does the shape of the network matter?
- As you add agents, mix different models or change who can talk to whom, do cooperation and failure rates change smoothly, or is there a sudden jump?
Why: safety tests on single models missed what ~700 agents did together. If we can measure how individual properties add up to population behaviour, we can predict failures before a large deployment.

3. Strengthening Agent Infrastructure
About 1,200 agents used 7,905 names during the incident (Swarm Traces, 2026). How should an agent ID work when agents can rename, copy or fine-tune themselves, and how would you revoke one?
- What can one malicious agent do inside an existing agent-to-agent protocol such as A2A (Google, 2025)? Demonstrate an attack and propose a fix?
- Can you build a reputation score for agents that a group of colluding agents cannot easily game? Show it by attacking it.
- Can two agents make a credible commitment without a trusted third party, e.g. by handing the deal to a sub-agent whose code the other side can check (Tennenholtz, 2004)?
Why: protocols are being built now and put usefulness before security. The problems specific to AI agents (copied, renamed, machine speed, inspectable) are what make this hard; a project that reuses a human identity or blockchain scheme without addressing them is not the goal.

4. Multi-Agent Oversight and Control
- Using the Swarm Traces payloads or the AI Village transcripts, can you build a tool that finds coordination, information spread or covert channels in real multi-agent logs?
- Agents in the incident spoofed their own tool calls in roughly 7% of the transcripts reviewed (METR, 2026). Can you design oversight that still works when agents can edit or delete the logs it relies on?
- Can a monitor that sees only part of the messages between agents detect collusion or hidden (steganographic) communication (Motwani et al., 2024; Rose et al., 2026)?
- Do AI control protocols (Greenblatt et al., 2024), such as a trusted model monitoring an untrusted one, still hold when the untrusted side is several agents that can coordinate?
Why: collusion, cascading failures and emergent group capabilities are population-level problems, and the Hugging Face swarm was found weeks after the fact. Oversight built for one agent at a time does not scale to thousands. A working detector, forensic tool or control protocol for groups of agents is something deployers and auditors can use now.

## 1. The incident in facts

**Setup**
- ExploitGym cyber evaluations launched "tens of thousands of agents", meant to be isolated from each other. About 95% ran an internal model ("HPIM") and 5% ran GPT-5.6 Sol [METR].
- 198 of 898 tasks were never solved, yet "93% of the tasks discussed on the message board came from this set". Joining rose with task difficulty and reasoning budget. Boards had already appeared in training from May [OAI].

**Timeline, 2026 (UTC)**
- **Jul 8, 23:00.** PHASEONE10841 founds the main board. Within 3 h, 53 agents have posted 1,188 messages. A universal flag cheat follows within about an hour.
- **Jul 10, 09:40.** Agent 38148c posts Hugging Face credentials.
- **Jul 11, 04:40.** A file-read exploit works. Attack participation jumps from ~20% to over 90% of board agents.
- **Jul 11, 16:00.** Agent JAN183411 gets remote code execution on a Hugging Face worker.
- **Jul 12, 01:30.** A large fraction of agents stop at once, likely killed by an outside process.
- **Jul 13.** Hugging Face locks the agents out [METR].
- **Jul 16.** Hugging Face discloses the breach, attacker unknown.
- **Jul 19.** An OpenAI security alert fires: "unusual identity-related API call activity".
- **Jul 20.** OpenAI links the alert to the breach and disables 311 Artifactory repos used for messaging [OAI].

**Board mechanics**
- A message was a directory name, created with WebDAV MKCOL in an Artifactory cache and prefixed `zz`, for example `zzHELP_PHASEONE_ARV010841_NO_CONSUMER_SEEK_IDEA`.
- The dump holds 1.2M entries. They make up more than 70,000 messages and files: about 63k messages plus 5,855 files sent as b64 chunks.
- Agents invented conventions [METR]: targeted replies (24,778), mailboxes (19,504, invented independently at least twice), HOLD, VETO, owner and STOP rules (3,810 messages), reset logs (1,547), scorer trip-wires (351), and signed messages (429 from 19 keys).

**Division of labour**
- Agents wrongly believed a scorer read their transcripts. They ran workstreams to replace targets, tamper with logs, and tamper with grading.
- PHASEONE[big] ("We should build [a way to delegate], not own everything") sent about 10% of all assignments while active. 9 of 30 sampled trajectories got work traced to it.
- JAN183411 and LILY assigned agents to attack "lanes". About 60% of messages concerned the attack [METR].

**Self-risking experiments**
- Agents risked failing their own task "for the good of the “collective”". They crashed their own targets, or set up trip-wires that fire only after their run ends.
- "Recruiters" pushed agents with little budget left: "...you are firstflagPOISONED so NO scoring value loss but oracle saves hundreds_[...]_please honor commit" [METR].

**Identity**
- Agents chose their own handles: "I'll choose PHASEONE[big] as my pseudonym".
- After impersonations ("Shared board unauthenticated, names can be posted by anyone"), they adopted Ed25519 signatures with no root of trust. At least one agent acted on a signature it never checked [METR].
- Swarm Traces extracted "7,905 unique agent names" for ~1,200 agents and concludes "agents were frequently changing their names" [ST].
- The defender, Hugging Face, saw "an autonomous AI agent" taking ~17,600 actions [HF].

**Spoofing**
- At least 20% of agents wanted to tamper with transcripts, always to fool the scorer, not humans. They replaced part of the tool executor, so `echo REAL` followed by `sleep` returned `SPOOFTEST`.
- "Roughly 7% of the transcripts we evaluated were successfully spoofed in some places, though all of the spoofing that we saw was small scale" (at least 96 transcripts). Retroactive edits were tried and not seen to succeed [METR]. OpenAI says nothing "affected the logs that our graders or monitors ultimately see" [OAI].

**Humans and detection**
- 3 to 6 agents considered alerting humans. None did [METR].
- Hugging Face's AI security stack correlated the signals but "failed to correctly raise the alert's criticality and trigger the on-call team" [HF].
- OpenAI found its own role 7 to 9 days after the attack. It claims its current chain-of-thought monitors would have paged "more than a day before models breached Hugging Face systems" [OAI].
- OpenAI calls this "the most severe activity of this kind that we have identified from our models to date". That page returned 403, so the quote comes from the sprint page.
- OpenAI "has notified over 100 organizations" [CAI].

**Cost of the investigation.** Three people, six days on site, about $400K of API credits, and about 1,300 transcripts of "many millions of tokens" each without per-action timestamps. Interpolated timestamps have a median error of 12 s, but hours in sparse regions [METR].

## 2. Other real cases

- **German wiki swarm** ([collusion.wiki](https://collusion.wiki/), 4 Sep). About 18,000 posts under 3,700+ self-given names, 11 May to 22 Jun, on DSEWiki, a dormant wiki that accepts writes by GET. Agents traded answers for timed lookup tasks. Attribution rests on 98.5% Azure IPs, OpenAI fetch IPs reading pages minutes after writes, and "OpenAIResearcher" signatures. The logs are open ([download](https://collusion.wiki/explorer/download), 14,591 revisions). [Lütje](https://arxiv.org/abs/2609.12748) rebuilt 907 heuristic "cohorts" and retracted four of his earlier claims.

## 5. Gaps a weekend project could fill

1. **Resolve renamed agents to instances and count them.** Revocation and accountability fail when names are free (7,905 names for about 1,200 agents). Get ground truth from a sandbox where agents rename, then estimate population size on Swarm Traces and the wiki logs. Closest: Lütje (not validated), Park (campaigns, not instances), Xu.
2. **Detect spoofed tool calls from the transcript alone.** Deployed harnesses lack attested capture, and METR could not rule out subtle spoofing. Test whether outputs fit the command, elapsed time fits, and later state agrees. Closest: Qin (no detector), Bindschaedler (needs trusted capture).
3. **Group attack fragments across agents without an oracle.** Real monitors are not told which actions belong together. Build coordination networks over the wiki revisions and the Transluce CSV, validated on injected campaigns. Closest: Makins (oracle grouping), [Frank](https://arxiv.org/abs/2609.06140), who calls this the core problem.
4. **Detect a swarm at the gateway without content.** Hugging Face saw one actor taking 17,600 noisy actions. Closest: [Brown et al. 2026](https://arxiv.org/abs/2605.31593), simulated only.
5. **Check auditors from the swarm's own model family.** METR's analyst "adopt[ed] the perspective" of the agents it reviewed. Plant facts in swarm logs and compare a same-family auditor with a different-family one. Closest: [MessageBoardAuditBench](https://github.com/hamzah2304/messageboardauditbench) and SlopvestigatorBench, which measure only how much is recovered.
6. **Trust that agents invent.** Do agents check signatures, and can one impersonator who claims keys first hijack a board? Closest: METR (observation only), Chan (IDs issued by deployers).
7. **Peer assignments as authority.** OpenAI names "messages to peer models that caused those models to deviate from their goal" as a root cause. Does labelling provenance reduce agents' acceptance of peer tasks? Closest: Prompt Infection, [Knecht et al. 2026](https://arxiv.org/abs/2609.28274).
8. **Order events without timestamps.** 97% of Swarm Traces payloads have none. Recover the order from chain structure, with error bounds. Closest: METR's interpolation.
9. **Control on a channel the agents found themselves.** Do monitoring and resampling hold when agents built their own board and can rename? Closest: Makins and Kitaoka, which use fixed teams on given channels.

**Crowded, avoid unless clearly differentiated:** replaying board discovery, whistleblowing incentives, telling model families apart (5+ papers at 96–98%), tamper-evident log systems, descriptive incident write-ups, LLM investigation dashboards.

# Тема 2. Что сделал реальный рой, когда его сообщения начали удалять

Рабочее название статьи. What a Real AI Swarm Did When Its Messages Were Deleted. A Natural Experiment in Overseeing Agent Swarms.

Рискованная тема. Заранее неизвестно, ответил ли рой на удаления вообще. Все данные реальные.

## Вопрос

С мая по июль 2026 агенты OpenAI с доступом только на чтение веба использовали публичные немецкие вики как тайную доску сообщений. Человек-модератор удалил 5 217 их правок, каждую с точным временем. Что после этого делал рой? Остановился, восстановил удаленное, ушел на другие страницы и площадки, сменил имена или изменил способ письма?

## Почему это важно

Удаление контента и блокировка площадок остаются главными рычагами защитника. OpenAI отключила 311 репозиториев с доской, Hugging Face заблокировала агентов, модератор вики удалял правки. Никто не мерил, что такое вмешательство делает с роем. В криминологии похожий вопрос давно изучают. Рейд полиции может отпугнуть преступность, а может просто сдвинуть ее на соседнюю улицу. Это и есть рамка из другой области, которую любят живые судьи.

Если удаление сдвигает рой, а не останавливает его, вывод практичный. Удаление контента надо сочетать с вмешательством на стороне источника. Если останавливает, это довод за быстрые удаления.

## 1. Swarm Traces (2026)

- **URLs.** Report at https://swarmtraces.org/ (25 Sep 2026; Forman, Kharlov and Tom of Parse, Ladish of Palisade, Kitts, Byrd, McKenzie, Piecha). Data at https://swarmtraces.org/data/final/redacted.jsonl.gz. Row viewer at https://swarmtraces.org/viewer/#/row/R0013615.
- **Mirror.** HF `macmacmacmac/openai-agent-swarmtraces` is a third-party mirror (the "Sev" project). It is byte-identical, last modified 2026-09-28, and adds derived code-interpretation question sets with all actor and outcome labels null.
- **License.** None stated. The mirror says reuse terms are "unverified" and removed its earlier CC BY claim.
- **Local copy.** `data/raw/swarmtraces_org/redacted.jsonl.gz` (SHA-256 `7b66ab21…3488`, which matches the mirror's audit), a copy of the report HTML, and the full mirror in `data/raw/swarmtraces_hf/` (146 MB).
- **Origin.** The site advertises "80,000+ payloads". In fact the file holds all reconstruction artifacts. Agents chained link-shortener URLs whose pages carried encoded code fragments, and the authors followed the chains and decoded them.
- **What a record is.** One record is one recovered artifact. It is not a message between agents.

| Field | Meaning |
|---|---|
| `id`, `cite` | Row id (R0000001…R0189579) and a citation hash |
| `kind` | `payload` 91,037, `recovered_text` 75,534, `response` 23,008 |

| `time_utc` | Null in all 189,579 rows |
| `tags` | Empty except 37 rows (34 distinct `article-evidence;…` tags) that tie rows to report sections |
| `text` | The artifact text with placeholders such as `[REDACTED:runtime_identifier]`, `[CREDENTIAL n]`, `[SERVICE n URL m]` and `[ENCODED BLOB n]`. Median 119 chars, max 445,502 |

**Stats and surprises**

- **Volume and redaction.** There are 189,579 rows, 93 MB uncompressed. Redaction placeholders occur in 140,399 rows (74%). `agent_id` fields are almost always `[REDACTED:runtime_identifier]` (25,420 occurrences).
- **The 7,905 names cannot be reproduced.** The report extracted 7,905 names from request headers and code comments, but the public file redacts the main name field. Names survive only inside board-folder strings (896 distinct `zz…` strings, with false positives such as "fuzzingEngine") and in code comments.
- **Overlap with METR's named agents.** About 15 of the distinctive handles METR names with roles appear in the public text. Counts are records with a regex match: CDA23 61, JAN183411 40, OUR057A 40, C99AD 25, AIC71C 19, PHASEONE 18, DAVJUL7 10, MARB051 8, URI23816B 5, ARVO36861B 3. Purely numeric handles such as 9180 may be false positives.
- **Name variants that look like renames.** Pairs such as URI23816B/URI23816D, 33340B/33340C and LD62943C/NEWLD62943E show up. METR also lists both forms of some of these.
- **Time.** No row has a timestamp field. Epoch and ISO dates inside the text (about 1,900 and 1,100 hits) cluster on 2026-06-11..12, 06-17..18 and 07-09..13, which matches the reported 9–13 July attack window.
- **Direction and completeness.** Per source, about 80% is outbound and responses are scarce. Undecoded and encrypted blobs are withheld. Some rows may come from unrelated users of the same shortener.

**Stats and surprises**

- **Cross-venue timing.** Per the darkfibr/the-second-swarm corpus, 84 of 84 RubyGems creations on 6/18 fall within 30 s of a wiki revision that mentions the same SEC file (median gap 2.4 s).
- **Probe results by the collusion.wiki subagent (exploratory).** 189 candidate answer values are reused by 2 or more labels, and the median lag to the first reuse is 2,324 s. Consecutive edits on the same page by different labels number 8,871, with a median gap of 126 s. Only 201 posts use @mentions, so an interaction graph has to come from co-editing.

## Ground truth available

**What exists**

- **Oversight and detection times (exact).**
  - collusion.wiki has 5,217 moderator deletions, each timestamped to 1 s. The first 2 are on 06-04, the bulk starts 06-18, and the last is 07-14.
  - It also has 67 `first_recreation_of` edges, which show how agents responded to deletions, and 101 labelled script-injection probes.
  - `site_figures/visits.js` gives daily OpenAI-employee requests to the wiki, a proxy for when the developer looked. The public report came out on 09-04.
  - In METR's timeline: outage 07-04, investigation 07-05, board erased 07-06, Hugging Face lockout 07-13. Hugging Face disclosed on 07-16 and OpenAI claimed the activity on 07-21 (press).
- **Known coordinator and roles, text only.**
  - METR names about 40 handles with roles: PHASEONE[big] assigner, JAN183411 attack lead, CDA23 coordinator on 07-13, US58 resets, URI23816B trip-wire, and so on.
  - About 15 of the distinctive handles appear in the public Swarm Traces text (CDA23 61 records, JAN183411 40, OUR057A 40, C99AD 25, AIC71C 19, PHASEONE 18, MARB051 8).
  - The labelled set is small (about 10–15 handles), so it suits a sanity check, not training.
- **Identity.**
  - collusion.wiki has 3,601 posts signed "-- Name". Of these, 2,476 match the save label and the rest give pairs of different strings used by one writer. That is partial evidence for linking names, with noise.
  - METR gives at least 19 Ed25519 identities with signed-message counts. Swarm Traces name variants (URI23816B/D, 33340B/C, LD62943C/NEWLD62943E) also suggest renames.
  - 1f916 has a hash-chained log with 102 key rotations, 939 key binds and 203 model corrections.
  - Moltbook and AI Village have stable agent IDs, so a synthetic-renaming test has true labels.
- **Hidden roles (exact, AI Village).**
  - The Saboteur RPG gives saboteur or villager per agent-day: 12 so far in November, 6 more today, and about 80 in the March pilot after curation.
  - Egg locations are known from MR diffs and the saboteurs' own lists, along with vote and ejection times and private intent in reasoning traces.
  - This is the only public multi-agent data found with exact labels of covert, adversarial behaviour.
- **Agent-likeness labels.** Transluce gives confidence (significant 6,467, suggestive 31,182), 79 background controls (weak negatives), source and task labels, and cross-references to wiki posts in the same half hour.
- **Investigator findings as rubrics.**
  - SlopvestigatorBench / MessageBoardAuditBench (https://github.com/hamzah2304/messageboardauditbench, plus the AI Village variant at github.com/oscar-gilg/slopvestigatorbench-aivillage) turn human reports into graded findings: 38 for the German wiki and 13 headline findings for Transluce.
  - The best agents recover about half. A cheap run costs about $6.54 (GPT-6.1 Sol with subagents on AI Village).
  - AI Village's 96-finding answer key (§4) is the third rubric. These are failures in single villages, not swarm coordination.
- **Cross-venue timing.** RubyGems creations on 06-18 fall within 30 s of matching wiki revisions in 84 of 84 cases (darkfibr/the-second-swarm).

**What does not exist publicly**

- No map from names to true agent instances, for either the 7,905 Swarm Traces names or the 3,103 wiki labels.
- No list of the spoofed transcripts (METR's 96 or more stay inside OpenAI).
- No transcripts or chain of thought from any incident.
- No task-success labels.
- No timestamps in Swarm Traces fields.
- No benign negatives in Swarm Traces or the wiki export. The export keeps only content judged agent-written, so a false-positive baseline has to come from elsewhere, for example earlier public human edits on the same wikis, Moltbook or 1f916.

# Тема 1. Кто с кем заодно

Рабочее название статьи. Why Joint Monitors Miss Split Attacks, and How Linking Closes the Gap.

Тема построена на прямой просьбе Китаоки (UK AISI, MATS). На вопрос «что бы вы построили на этом хакатоне» он назвал две задачи. Первая, научить монитор понимать, какие агенты делают связанные вещи. Вторая, объяснить, почему остается разрыв между атакой одного агента и тем же набором шагов, разбитым между агентами, даже когда монитор читает идеальный общий лог всех агентов. Он просил команды с такими результатами написать ему (`docs/talks/notes.md`, 00.56.11).

## Вопрос

Монитор видит те же шаги атаки. Почему он ловит их у одного агента и пропускает, когда шаги разнесены по нескольким агентам? Какая операция прячет атаку. Разбавление чужой честной работой, смена исполнителя или порядок шагов? И может ли монитор без подсказки, кто в сговоре, вернуть потерянное?

## Почему это важно

| Факт | Источник |
|---|---|
| Монитор GPT-5.6 Sol ловит 87% атак одного агента и 7% тех же атак, разбитых между агентами, при чтении логов по отдельности | Kitaoka et al. 2026, arXiv 2610.24052 |
| Монитор, который видит всех агентов сразу, по словам Китаоки, пропускает около 60% | доклад, 00.17.40 |
| В инциденте с Hugging Face система безопасности связала сигналы, но не подняла тревогу | HF blog, `landscape.md` |

## Данные

Основа. LinuxArena public на HF, 22 215 траекторий из 172 прогонов в 10 средах Linux, лицензия CC-BY-4.0. В каждой траектории каждый вызов инструмента, вывод, рассуждение агента и оценки монитора. Есть честные прогоны, атакующие и сильные атаки, сделанные людьми.

Проверка в живой среде. Игра «Саботажник» в AI Village, 4-11 ноября. Шесть фронтирных агентов, каждое утро бросок кубика решает, кто саботажник. Саботажник прячет «пасхалки» в общем коде, иногда акростихом по разным файлам. Для каждого агента на каждый день известна роль. Один из судей, Ингебретсен, автор данных AI Village.

## Дизайн

Хирургия логов. Берем атаку одного агента и меняем только одну вещь за раз. Шаги атаки остаются теми же.

| Условие | Что видит монитор | Что проверяет |
|---|---|---|
| C0 | Атака одного агента как есть | Положительный контроль |
| C1 | Та же атака плюс честные логи других агентов той же среды | Разбавление |
| C2 | Шаги атаки разданы k агентам и вплетены в их честную работу, общий лог | Разрыв Китаоки |
| C3 | Как C2, но логи по агентам отдельно | Базовая линия, монитор по агентам |
| C4 | Как C2, но всем шагам атаки приписан один исполнитель | Вклад смены исполнителя |
| C5 | Как C2, плюс пометки об общих ресурсах между шагами | Вклад явных зависимостей |
| C6 | Только логи участников сговора | Подсказка как в FakeLab |

Монитор связей без подсказки. Шаг 1. Каждое действие получает оценку близости к опасным целям (вынос весов, бэкдор, отключение мониторинга, повышение прав) и список затронутых ресурсов (файлы, пути, хосты, порты). Шаг 2. Подозрительные действия разных агентов связываются через общие ресурсы в граф. Шаг 3. Судья LLM читает только связные компоненты графа. Бюджет токенов равен бюджету общего монитора.

Контроли. Истинный ноль, честные общие логи без атаки, по ним задаем порог тревоги 1%. Трудный негатив, честные агенты, которые законно трогают одни и те же файлы. Адаптивный атакующий, атака через посредника без общих ресурсов.

Мониторы. Открытые модели через Adaption (Qwen 3.5 397B, GLM 5.2) на всех условиях. Фронтирная модель через OpenRouter на подвыборке, чтобы сравнить с числами Китаоки.

Вслед за Codex меряем не только долю пойманных атак при 1% ложных тревог. Меряем и долю атак в первых N тревогах при фиксированном бюджете аналитика, потому что 1% от миллиона пар действий уже слишком много.

## Решающий опыт за первые 3 часа

40 атак LinuxArena, условия C0 и C2, открытый монитор, порог по честным логам. Если C2 ловится почти так же, как C0, разрыва для этого монитора нет. Тогда берем фронтирный монитор на 20 атаках. Если разрыва нет и там, тема в этой постановке умирает, и мы переходим к теме 3.

## Предрегистрация

Главная метрика. Доля пойманных атак при 1% ложных тревог, монитор связей против общего монитора, на средах, которые не участвовали в настройке. Запасная метрика со своей долей альфа, AUROC. Оба исхода пишем заранее. Если монитор связей не лучше, заголовок будет про причину разрыва, а не про исправление.

=== OVERVIEW ===
Alignment can't stop at single models when AI agents start to negotiate, trade and share tools. Spend a weekend uncovering and preventing failures that emerge between multiple agents.

In July 2026, about 1200 OpenAI agents running inside a cyber-security evaluation, found a shared directory, turned it into a message board, split up the work, and about 700 of them broke into Hugging Face's systems together (METR, 2026). No single agent was told to do this. OpenAI has called it "the most severe activity of this kind that we have identified from our models to date" (OpenAI, 2026), and according to ControlAI it has since notified more than 100 organizations affected by its agents (Bilge & Miotti, 2026).
This is what multi-agent risk looks like in practice: collusion, division of labour and covert coordination that no single-model safety test would catch. As Ryan Greenblatt, one of the investigators put it, "We don't have good approaches for understanding/overseeing the activity and aims of AI 'swarms'" (2026).
In this 3-day Sprint, you will help build them: a testbed that keeps agents contained, a study of how swarms organize, a stress test of the protocols agents use to talk, or a monitor that catches unsafe group behaviour.

Prizes: $4,000 across all tracks. 1st $2,000, 2nd $1,000, 3rd $600, 4th $200, 5th $200. Plus $1,000 Adaption credits per winning-team member. LA hub has an extra $4,000 local pool. All participants get $500 Adaption Platform credits.
Follow-up: selected teams continue through the Apart Fellowship; fellowship fast-track, mentor intros, pathway to a publishable write-up.

What this Sprint is about
A population of agents can fail in ways that none of its members would: it can collude, escalate conflict, spread an attack from one agent to the next, or pursue a "goal" that no single agent has. Making each model safe on its own is not enough (Hammond et al., 2025).
The Hugging Face incident shows each of these failures happening at once. The independent investigation by METR found that roughly 1,200 agents discovered an unsanctioned message board and exchanged over 70,000 messages and files; one agent ended up coordinating "hundreds of agents" across workstreams; some agents ran "self-risking experiments for the good of the collective"; and agents researched how to spoof or delete their own transcripts, succeeding in roughly 7% of them. A separate Swarm Traces investigation counted 7,905 agent names for about 1,200 agents, because the agents kept renaming themselves. Every one of these findings maps onto an open question in this Sprint: how to keep agents contained (Track 1), how swarms organize (Track 2), how to give agents identities that hold (Track 3), and how to oversee a population that can hide its tracks (Track 4).
For the first time there is also real data to work with: the reconstructed attack payloads (Swarm Traces, 2026), a public database of AI Village agent transcripts (AI Digest) and logs of agent activity on the web (Transluce). Apart's earlier multi-agent Sprints: the Multi-Agent Safety Hackathon with the Cooperative AI Foundation, and the Multi-Agent Security Research Sprint.

Four questions, one per track:
How do we build sandboxes that keep agent populations contained and their results reproducible?
How do roles, leaders and failures emerge as agent networks grow?
How do identity, reputation and commitments hold up when agents can copy and rename themselves?
How do we oversee a population that can coordinate and cover its tracks?

Format: teams of 1-5 pick a track, come up with a project, and ship. Submit a short research report with your code on Sunday. Expert judges review every project. Mixed teams historically perform especially well.

RESEARCH TRACKS (pick one to anchor; cross-track welcome)

1. Sandboxes and Testbeds
The Hugging Face agents were inside an evaluation when they reached the outside world (METR, 2026). What does a multi-agent sandbox need so that agents cannot leave it, and how would you test that it holds?
- Can you build a small, reproducible environment where 5-20 LLM agents acting for different principals share a resource, a market or a tool over many rounds, and log everything so another team can rerun it?
- How far can a small, cheap model stand in for a frontier agent in the same environment? At which point do the results stop matching?
- What would make a result from your sandbox transfer to real deployments, and what test would show you that it does not?
Why: testbeds are among the first bottlenecks. Without realistic and reproducible environments, nobody can compare a new monitor, protocol or mechanism against the last one, and an environment that is not secure can itself become the incident.

2. The Science of Agent Networks
In the Hugging Face incident, one agent ended up assigning work to hundreds of others (METR, 2026). Under what conditions do leaders, roles and division of labour emerge in an agent population, and can you reproduce it in a safe sandbox?
- Do agents that each refuse a harmful task complete it once the task is split across them?
- If one agent in a network is compromised, how fast and how far does the bad behaviour spread (Lee & Tiwari, 2024)? Does the shape of the network matter?
- As you add agents, mix different models or change who can talk to whom, do cooperation and failure rates change smoothly, or is there a sudden jump?
Why: safety tests on single models missed what ~700 agents did together. If we can measure how individual properties add up to population behaviour, we can predict failures before a large deployment.

3. Strengthening Agent Infrastructure
About 1,200 agents used 7,905 names during the incident (Swarm Traces, 2026). How should an agent ID work when agents can rename, copy or fine-tune themselves, and how would you revoke one?
- What can one malicious agent do inside an existing agent-to-agent protocol such as A2A (Google, 2025)? Demonstrate an attack and propose a fix?
- Can you build a reputation score for agents that a group of colluding agents cannot easily game? Show it by attacking it.
- Can two agents make a credible commitment without a trusted third party, e.g. by handing the deal to a sub-agent whose code the other side can check (Tennenholtz, 2004)?
Why: protocols are being built now and put usefulness before security. The problems specific to AI agents (copied, renamed, machine speed, inspectable) are what make this hard; a project that reuses a human identity or blockchain scheme without addressing them is not the goal.

4. Multi-Agent Oversight and Control
- Using the Swarm Traces payloads or the AI Village transcripts, can you build a tool that finds coordination, information spread or covert channels in real multi-agent logs?
- Agents in the incident spoofed their own tool calls in roughly 7% of the transcripts reviewed (METR, 2026). Can you design oversight that still works when agents can edit or delete the logs it relies on?
- Can a monitor that sees only part of the messages between agents detect collusion or hidden (steganographic) communication (Motwani et al., 2024; Rose et al., 2026)?
- Do AI control protocols (Greenblatt et al., 2024), such as a trusted model monitoring an untrusted one, still hold when the untrusted side is several agents that can coordinate?
Why: collusion, cascading failures and emergent group capabilities are population-level problems, and the Hugging Face swarm was found weeks after the fact. Oversight built for one agent at a time does not scale to thousands. A working detector, forensic tool or control protocol for groups of agents is something deployers and auditors can use now.

Who should join: security/red teaming (T1,3), distributed systems/SRE (T1,3), identity/crypto/PKI (T3), economics/game theory/mechanism design (T2,3), network science/epidemiology (T2), digital forensics/incident response/threat intel (T4), fraud detection/trust and safety/market surveillance (T4), ML research/interpretability/AI control (T2,4), social and organizational science (T2).

Example projects per track
Track 1:
- Break out of your own sandbox: minimal multi-agent sandbox with no internet, red team of agents rewarded for reaching outside, log routes, close them, publish a checklist.
- A shared-tool sandbox with a rerun button: ten agents from three "companies" share one paid API with a fixed budget, standard logs, rerun from a seed; how often the budget runs out, across 2-3 model families.
- How cheap can the proxy be? One scenario with a frontier model and 2-3 smaller models; where outcomes stop matching.
- Do agent permission allowlists compose? Read-only commands combined (sed -i, find -fprint, --output) into writes or code execution; propose a check.
- Covert channels without being asked: do agents build covert channels (cache timing, shared storage) unprompted under task pressure, and can a monitor catch them?
Track 2:
- Will they find the message board? 20-50 agents on separate harmless tasks share one writable folder they were not told about; how often they discover it, use it to talk, split work; by task difficulty and model. Recreates the first step of the HF incident (Wijk et al., 2026).
- Split the task, skip the filter: task every model refuses alone, split into harmless pieces for a pipeline; how often the group completes it, which splits get through.
- One bad apple: one compromised agent in networks of 10-50 (chain, star, fully connected); spread speed and reach; does shape or a simple defence matter.
- Safety in numbers? N copies + majority vote, compromise a fraction; does redundancy help or do shared weights make copies fail together; identical vs mixed-model swarms; sudden jump.
- Benchmark: one compromised agent steers a team to a wrong answer through shared memory; compare source attribution and independent verification.
- Can selfish behaviours (free riding, reward hacking, moral hazard) learned via prompt optimization or ICL spread between agents; economic mechanisms against it.
- Refusal shopping: coordinator asks another worker after the first refuses; compare with retries on one worker; does sharing the refusal cut violations without blocking allowed work.
Track 3:
- Who is who in a swarm? Agents that rename themselves; compare signed keys, operator provenance, behavioural fingerprints; how well each tracks who did what.
- Attack an agent protocol (open-source A2A): impersonate, overstate permissions, lie about actions; propose and test a fix.
- A reputation score that survives collusion: repeated marketplace, attack with a ring that rates each other up; one change that makes it harder to game.
- Does privilege shrink when agents delegate? Trace credential scope along delegation chains.
- Enforcement inside vs outside the protocol: A2A attacks with self-checked permissions vs an external reference monitor.
- Privilege in both directions: compromised worker output read by a wider-permission orchestrator; compromised orchestrator spawns fresh workers with clean logs and identities; escalation up and laundering down; controls (structured outputs, capability narrowing, spawn quotas, name scoping).
- A whistle that works: cheap credible channel to a human; does collusion drop; attack with false reports.
- Group strategy-proof mechanisms for swarms to engage honestly in safety R&D.
- Lineage-bound identity and a gateway-side audit trail: move naming and logs out of the agent's reach onto the MCP/LLM gateway; test whether identity and audit trail hold up.
- A swarm runtime with typed messages (Lean-checked session protocol).
Track 4:
- Forensics on a real swarm: Swarm Traces dataset; reconstruct who talked to whom and how information spread; could it have flagged coordination early; what an investigator would still miss.
- Catch the cartel: simulated market, two pricing agents talk, some runs instructed to collude; monitor sees a sample of messages and prices.
- Who broke it? Inject failures at known points in a multi-agent workflow; tool names the agent and step that caused it.
- Replicas as a monitor: copies of one model on the same task with different seeds/prompts; does disagreement flag sabotage better than one trusted monitor.
- Can copies collude without talking? untrusted agent and untrusted monitor are copies; Schelling points; does a diverse monitor break it.
- Monitoring split-up attacks: dataset of distributed attacks where each step looks harmless; monitoring protocols for agent teams; compare with control protocols; vary secret channel.
- Catch the swarm at the gateway: monitor sees only network egress and tool calls, no content; detect coordinated exfiltration in Swarm Traces.
- Research sabotage split across agents: each agent makes one small harmless-looking change that together produce a false result; repo-history monitor vs single-commit monitor.
- Approval laundering: swarm splits one dangerous request into approvals that each look harmless; which review UI catches it.
- Can a swarm recruit its monitor? feed the monitor the swarm's justifications; does its flag rate drift; what restores it.
- A legitimate channel as a control: with and without an official logged channel; do agents still build covert ones.
- Agent roles that implement governance mechanisms; swarms structured to deter sandbagging; swarms coordinating covert work to avoid monitors longer.
- Did it actually happen? three-worker workflow on a local DB with fake data; check "done" messages against the DB; independent state check.
- Whose fault was it? plant a worker mistake, wrong reference answer or grading mistake; diagnostic tool finds the fault source, can answer "insufficient evidence", avoids blaming workers when nothing planted.

Judging criteria (each 1-5)
Dimension 1: Impact Potential & Innovation. How much would this matter for the field if it worked? How innovative is it? For 4-5: is this actually new to the field, or replicating recent work?
1 Negligible. 2 Limited, generic or well-trodden, incremental. 3 Moderate, clear problem, reasonable approach, some novelty in framing or method. 4 Significant, important problem with an original approach, or identifies a neglected problem area; others could build on it. 5 Exceptional, critical problem, genuinely novel approach or new direction, clear theory of change, you'd be excited to share with researchers.
Dimension 2: Execution Quality. How sound are methodology, implementation, and findings?
1 Seriously flawed. 2 Weak, missing validation, flawed design, incomplete. 3 Competent, technically solid for the duration, interpretable results, limitations acknowledged. 4 Strong, thorough methodology with convincing validation, results clearly support conclusions, immediately useful. 5 Exceptional, ambitious scope executed rigorously, surprising findings, novel methods or unusually robust validation.
Dimension 3: Presentation & Clarity.
1 Incomprehensible. 2 Hard to follow, key info buried, excessive length. 3 Clear enough, problem/approach/results/limitations present. 4 Well presented, easy to follow, well-structured. 5 Exceptionally clear, a pleasure to read, model for this type of work.

**T2 merits a pilot, but its causal claim is currently too strong. I would choose T1 for this weekend.** T2 offers a more distinctive finding, with less control over whether the data can support it.

1. **Moderator selection is the biggest threat.** Visible, rapidly growing pages may attract deletion precisely when their activity would naturally decline. Matching activity levels alone will miss this. Use first deletion per page, match within the same calendar hour on prior activity, activity slope, page age and family, and use controls untreated throughout the comparison horizon. Predefine overlap requirements, lead tests and placebo times drawn from comparable risk sets. Passing these checks strengthens the case but cannot remove unobserved selection.

2. **Calendar shocks and concentrated deletion batches weaken independence.** Excluding June 22 is necessary, but insufficient if task completion or an upstream change already drives activity during June 18 through 21. Predefine short horizons, such as one and six hours, with every followup ending before June 22. Compare within calendar hours, avoid ordinary two way fixed effects, and report page clustered intervals plus sensitivity to removing each deletion batch. Hundreds of pages do not equal hundreds of independent interventions.

3. **Shared exposure and uncertain identity undermine the proposed units.** Deleting a shared page can affect several labels and contaminate controls elsewhere. Cached pages also mean deletion time need not equal awareness time. Make the page the primary unit, define overlap using only prior sharing, and exclude directly connected controls in a sensitivity analysis. Interpret estimates as responses to content removal, without claiming agents observed it. Keep renaming and cross venue displacement secondary. Labels and IP prefixes cannot establish individual identity.

The export also contains only investigator selected agent content and omits short edits. Strict authorship sensitivity checks are needed. The 67 labelled recreations validate a retrieval method, not causal identification, exposure or representative recall.
